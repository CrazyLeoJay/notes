# 自动注册插件设计

> 所有的预设是在 Jvm 平台下实现

插件，一般实是预先设计好功能的一套接口，然后通过某种方式获取这个接口的实例，然后去调用其功能的方式。如果没有获取到，就按照没有处理。

## 什么时候需要用到

- 通过对业务的归类总结，有相同行为的模块。可以被抽象为工厂的模块，且需根据实际情况进行加载的。比如接入市面上各家应用市场、接入各家买量媒体平台等。
- 有些单一功能可有可无，但需要根据不同的场景进行添加或者删除。

## 实现方式

### 反射

根据开发时候的需求，插件需要有唯一性，即一种类型的插件，同一时刻，只需要实现一种即可。所以先设计规范，规定这个类型的插件必须实现在**指定路径类名**中，使用**指定的方法**，返回一个插件接口类型的**单例对象**。

这样的好处是：

- 当单例类存在时，插件生效，如果不存在，则不生效。
- 如果意外引入了两个同类型的库，会在代码编译阶段报错，提示有相同类冲突。
- 使用单例，不需要额外存储实例，在不同的模块中调用时，不会出现对象丢失的问题。

当然，也可以通过其他方式去实现，但需要复杂的定义。如果需要实现插件的多个实现，可以使用 Jvm SPI 机制。

### Jvm SPI 服务发现机制

> 这是一个很容易被忽略的特性。并且我还没有有验证过是否可以在 Android 上实现，毕竟 Android 底层虽然时 jvm，但不知道是否进行了魔改，是否保留了这个功能。但大概率是有的。

SPI 本质上是"**基于接口的编程＋策略模式＋配置文件**"组合实现的动态加载机制：

1. **定义服务接口**：由框架或核心库定义
2. **提供实现类**：由第三方提供具体实现
3. **配置文件声明**：在`META-INF/services/`目录下创建以接口全限定名命名的文件，内容为实现类的全限定名
4. **服务加载**：通过`ServiceLoader`类动态加载实现类

即实现：

1. 我们可以在**公共 library**中配置**插件 API 接口**
2. 在插件实现的项目（**插件 Library**）中，添加**公共 Library**项目，
3. 在**插件 Library**中创建服务文件：`classpath:META-INF/services/{这里文件名是定义插件类的全路径名称}`，
4. 在服务文件中，每一行写入**插件 API 接口**的**实现**类的全路径。
5. 在**核心代码中（主程序）**中通过**ServiceLoader.load(MyPlugin::class.java)**调用获取。

> 可以直接使用[Google 的 Auto 库](https://github.com/google/auto/tree/main/service)。可以帮忙自动注册。

注意的点是，由于**ServiceLoader**重写了**Iterable**，通过 **SeSrviceLoader**获取插件服务后，**在遍历时**才会创建实例，并且是**每次遍历**都会去**重新创建**，如果需要保证调用，需要主 SDK 进行实例**缓存**。

## 实现方式比较

|          | 反射方式                                                                                                                                                                 | Jvm 服务注册                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 实现方式 | 根据规则定义，通过指定类或者方法获取到指定的对象。                                                                                                                       | 通过配置文件的定义，存在多个实例类型，每次遍历都会创建新的实例                                                                                                                     |
| 优势     | 实现简单，仅需要简单的约定，插件双方都去遵循即可。                                                                                                                       | JVM 原生支持。并且仅需要维护 Api 接口，可以通过现成的插件动态注册 SPI 配置到 META-INF 中。                                                                                         |
| 劣势     | 如果插件较多，需要维护文档，在每次创建插件时，都要去查阅，并且核对是否配置正确。反射内容较多需要扎实的编码功底去处理反射实现。处理不当可能造成内存泄漏、定义混乱等问题。 | 没有固定的单例实现，需要通过遍历实现，底层重写遍历，每次获取都会通过反射去创建实例，所以不管是需要限制单例实现还是需要多实例，都需要在第一次初始化时处理并且在程序中保存实例对象。 |

## 反射方式劣势优化

可以通过注解编程，将反射实现的规则代码化。注解编程也是通过 Jvm 的 SPI 机制去实现的，只不过在使用上有所区别。

为每个模块都定义一个注解，每个注解都按照设计逻辑去生成实体类，在使用时，直接让插件项目实现注解，并且为实现实体添加该注解，这样会自动生成模板代码，简化实现。
